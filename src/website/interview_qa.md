线程池
1. 线程池刚创建时，里面没有一个线程。任务队列是作为参数传进来的。不过，就算队列里面
有任务，线程池也不会马上执行它们。
2. 当调用 execute() 方法添加一个任务时，线程池会做如下判断：
a) 如果正在运行的线程数量小于 corePoolSize，那么马上创建线程运行这个任务；
b) 如果正在运行的线程数量大于或等于 corePoolSize，那么将这个任务放入队列；
c) 如果这时候队列满了，而且正在运行的线程数量小于 maximumPoolSize，那么还是要
创建非核心线程立刻运行这个任务；
d) 如果队列满了，而且正在运行的线程数量大于或等于 maximumPoolSize，那么线程池
会抛出异常 RejectExecutionException。
3. 当一个线程完成任务时，它会从队列中取下一个任务来执行。
4. 当一个线程无事可做，超过一定的时间（keepAliveTime）时，线程池会判断，如果当前运
行的线程数大于 corePoolSize，那么这个线程就被停掉。所以线程池的所有任务完成后，它
最终会收缩到 corePoolSize 的大小。



MYSQL结构 
什么是叶子节点（leaf node）
● 位置：最底层的节点（树的最后一层）
● 作用：真正存放“查到的数据条目”
● 存什么（分两种索引）：
  a. 聚簇索引（Clustered Index，主键索引）
    ■ 叶子节点存：主键 + 整行数据（完整记录）
  b. 二级索引（Secondary Index，普通索引）
    ■ 叶子节点存：索引列的值 + 主键值（不是整行）
    ■ 查整行时还要“回表”：拿主键再去聚簇索引的叶子节点找整行
另外，B+ 树的叶子节点通常还会用指针串成有序链表，方便范围查询（BETWEEN、ORDER BY、LIKE 'xx%' 这种）。

● 出现 Using index condition 不一定覆盖索引（这是 ICP，和覆盖索引不同）
● 联合索引是否回表？
  ○ 二级联合索引：通常要回表（叶子只有索引列 + 主键）
  ○ 但如果查询的列都在这个索引里 → 覆盖索引 → 不用回表
● 最左前缀原则
idx(a,b,c) 能用到：a / a,b / a,b,c
不能直接用：b 或 c（除非优化器有其它策略，但面试按原则答）

Redis 分布式锁
SETNX lock 1      # 抢锁：只有第一个能成功
EXPIRE lock 10    # 给锁加 TTL：10 秒自动释放
1. 获取锁的时候，使用 setnx（SETNX key val：当且仅当 key 不存在时，set 一个 key
为 val 的字符串，返回 1；若 key 存在，则什么都不做，返回 0）加锁，锁的 value值为一个随机生成的 UUID，在释放锁的时候进行判断。并使用 expire 命令为锁添加一个超时时间，超过该时间则自动释放锁。
2. 获取锁的时候调用 setnx，如果返回 0，则该锁正在被别人使用，返回 1 则成功获取
锁。 还设置一个获取的超时时间，若超过这个时间则放弃获取锁。
3. 释放锁的时候，通过 UUID 判断是不是该锁，若是该锁，则执行 delete 进行锁释放。
1) 最大问题：SETNX 和 EXPIRE 分开写不原子
很多人写成：
1. SETNX lock 1
2. EXPIRE lock 10
如果在 1 成功后、2 还没来得及执行时进程崩了/网络断了，这把锁就没有过期时间 → 死锁（永远没人拿到锁）。
✅ 正确做法：用 Redis 的原子命令
● SET lock `<uniqueValue>` NX EX 10（或 PX 毫秒）
2) 没有“唯一标识”会导致误删别人的锁
如果你解锁时直接 DEL lock，可能发生：
● 线程 A 拿到锁（10s）
● A 卡住超时，锁过期
● 线程 B 拿到新锁
● A 恢复执行，直接 DEL lock → 把 B 的锁删了（严重并发安全事故）
✅ 正确做法：
● 锁 value 存一个 唯一 token（UUID/线程标识）
● 解锁用 Lua 脚本原子校验：只有 value 还是我的 token 才能删
（伪逻辑：if get(lock)==token then del(lock) end）

缓存雪崩的情况：大量缓存本来应该查缓存的命中缓存的全去命中数据库了导致的，解决方案：
1.加锁排队，缓存失效了，再建立缓存就好了，问题是大量请求进来的时候，太多人同时set更新缓存，加锁，只让一个缓存成功。
也可以直接给他降级请求，提示系统繁忙，稍后再试给他。
剩下的给他一定的重试时间，再重新查是否存在。
2.设置不同的过期时间
缓存穿透：虚假的请求多次查redis和db，或者绕过db。
解决：布隆过滤器，提前过滤，不合适的请求不给他查。查不到的key也给他缓存，然后给一个很快的过期时间5分钟，然他命中这个空缓存，这样对db就没有压力了。


事务消息
为什么需要事务消息？
举个订单→库存的例子：
● 订单服务：落单（写数据库）
● 库存服务：扣库存（靠 MQ 消费订单事件）
如果没有事务消息，可能出现：
1. 订单写库成功，但消息没发出去 → 库存永远不扣（不一致）
2. 消息发出去了，但订单写库失败/回滚 → 库存扣了但订单不存在（更糟）
事务消息就是为了避免这两类“半成功”。

事务消息怎么做（两种主流实现）
1) 本地消息表 / Outbox（最常用、最稳）
订单服务在同一个数据库事务里做两件事：
1. 写订单表
2. 写消息表（outbox，记录要发的消息，状态=待发送）
事务提交后：
● 后台线程/任务把 outbox 里的消息投递到 MQ
● 投递成功再把消息状态改成已发送
● 若投递失败：重试（定时扫描 outbox）
优点：实现简单、强可靠、跟 MQ 无强耦合
缺点：有一点延迟，需要扫描/重试机制
你简历里“跨服务场景基于事务消息最终一致性”一般就是这套（或类似）。
2) MQ 自带事务消息（某些 MQ 支持）
比如有的 MQ 支持 “半消息/预消息 + 事务提交/回滚 + 回查”：
● 先发半消息（消费者不可见）
● 本地事务成功 → 提交消息（消费者可见）
● 本地事务失败 → 回滚消息（消费者不可见）
● 如果生产者挂了，MQ 会回查生产者事务状态
优点：不需要 outbox 表
缺点：依赖具体 MQ 特性，系统复杂度更高

面试官最常追问的 3 个点
1. 最终一致性怎么保证？
outbox 里未发送的消息持续重试，保证“最终会发出去”
2. 重复消息怎么处理？
消费端做幂等（orderId / msgId 去重），因为 MQ 通常是“至少一次”
3. 失败怎么补偿？
重试/死信队列 + 补偿任务（回滚库存、标记订单失败等）

一句话总结：事务消息就是“本地事务 + 可靠发消息”的一致性方案，用来做跨服务最终一致。


JVM的内存结构
JVM 内存结构主要分为以下几个部分：
可用于线程之间共享的数据 常量池、堆（放对象的）、方法区（放类信息、静态变量等）

JVM
当jvm中的数据准备好之后，hotpot就会新建一个java线程，同时操作系统也会新建一个线程，这两个线程之间具有映射关系，java线程的生命周期由hotpot管理，java线程的调度由操作系统管理。每个java线程都有一个程序计数器、一个虚拟机栈和一个本地方法栈，这些都是线程私有的内存区域。程序计数器用于存储当前线程执行的字节码指令地址，虚拟机栈用于存储方法调用和局部变量，本地方法栈用于存储本地方法调用的信息。
JVM 内存区域主要分为
线程私有区域【程序计数器、虚拟机栈、本地方法区】、线程共享区
域【JAVA 堆、方法区】、直接内存
